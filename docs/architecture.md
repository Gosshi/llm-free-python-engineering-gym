# Architecture decisions

## 初回の選択

初回診断はPython 3.13.0を使用する。ローカルに利用可能な安定版であり、型ヒントを
自然に使いながら、Pythonの標準的な実装力を測れるためである。FastAPIとPydanticは、
小さなHTTP APIで入力検証、HTTP表現、責務分割を同時に観測できるため採用する。

保存先はインメモリに限定する。これにより、SQL、接続、ORM設定、Dockerなどのセット
アップ要因を診断から除き、CRUD、データの所有、検索、例外、APIの基本へ集中する。
データモデルは識別子と明確なフィールドを持ち、後にPostgreSQLへ永続化できるように
設計する意図を問う。一方、初回はORMと実データベースを採用しない。

## 開発環境

ローカルで利用できる `uv` をパッケージ管理とコマンド実行に採用する。`pyproject.toml`
に依存関係とツール設定を集約し、`.python-version` でPython 3.13.0を固定する。初回
セットアップは `uv venv --python 3.13.0` と `uv sync --dev` で完結する。

pytestは課題の公開テストを実行し、FastAPIのHTTPテストクライアントを利用する。Ruffは
構文、基本的な品質、import整理、現代的なPython記法を軽量に確認する。初回では厳格な
mypy対応を主目的にしないため、mypyは導入しない。型ヒントはレビュー項目として評価し、
必要性が高まった段階で段階的な型検査を追加する。

## 拡張方針

結果に応じて、次の課題を一つずつ追加する。基礎が十分ならSQL、PostgreSQL、SQLAlchemy、
Alembic、認証認可、非同期、外部API、キャッシュ、バックグラウンドジョブ、性能、障害
調査へ進む。基礎で停止した場合は、関数、データ構造、疑似コード、読解、デバッグ、
境界値テストなど小さな課題へ戻る。

FastAPIの記法を覚えているかと、要件を読み、状態を扱い、失敗を設計し、説明できるかは
別の能力である。テストとルーブリックでは両者を分けて扱い、フレームワーク固有知識の
不足だけで一般的な実装力を低く断定しない。
